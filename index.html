1. 目标：配置化（冷热分流）

类别内容处理
热（频繁更新）新增因子、修改公式权重、因子内部的常数权重等配置化，统一收口
冷（很少迭代）很细粒度、稳定的代码（如特殊排序/置换/统计算法）不必配置化

约束（不是目标）：迁移保持旧链路数据流、数值、顺序等价；float/double 逐位一致尚未验证。

3. 四个方案

方案一 外流（已有做法）：C++ 因子 + DSL 拼装 + F1 公式

flowchart LR A["5000行 finalscore"] --> B["多个 C++ 因子（admit/compute，可嵌套 factor udf）
零散配置"] --> C["DSL 小算子拼大算子
零散配置"] --> D["F1 最终公式（配置化）"]

加一个因子要改：C++ 因子 + DSL + 公式，需上线。

✅ 最后的 F1 公式已配置化；中间 C++ 因子、DSL 也有零散配置；表达能力等价原 C++。
❌ 配置没有统一收口：散在 C++ / DSL / F1 三处，代码分散难找，因子能否复用没人知道。
证据：common_se_defs.h:145 FINISH_ADMIT、:164 FINISH_COMPUTE

方案二 C++ 前处理 + F1 + C++ 后处理

flowchart LR A["C++ 前处理（冷，不涉及配置）"] --> B["F1 公式（热，全部配置）"] --> C["C++ 后处理（冷，不涉及配置）"]

方案一配置分散痛点的升级：热内容放 F1；很少迭代的放前/后处理 C++，不涉及配置。

✅ 热内容在 F1 收口。
❌ 把本来业务聚集的代码按阶段拆分，方案代价不合理（例：PC 置换须在主公式后、AUC 在中间、top61 在两轮之间，同一业务被切到多段）。

方案三 KaiFG + F1

flowchart LR K["KaiFG 因子（复杂逻辑，DSL）"] --> D["DSL 聚合"] F["F1 公式（热代码，配置）"] --> D --> W["写回"]

KaiFG 只需 DSL，F1 是配置，两者通过 DSL 聚合；热代码走 F1，复杂逻辑走 KaiFG；全程只有 DSL 和配置。

✅ 不写 C++；表达力足够。
❌ 仍是“因子 + 公式”的抽象；因子迭代不是配置化，还要上线。
证据：KaiFG 编译加载为进程级 call_once（kaifg_client.cc:393-411），不支持热更。

因子等复杂逻辑用 UDF，整体转化成多种 F1 公式组合，全量走配置文件。

✅ 热内容全部配置、统一收口。
❓ 待讨论：

  1. 配置文件怎么管理？
  2. UDF 用起来也是开发 C++。
  3. 真实需要 UDF 的数量多吗？
  4. 能不能复用？

另：F1 注册 UDF 目前是集中注册，不是插接式（f1_udf_collection.h:558），需向 F1 团队提需求。

6. 风险与待决问题

  1. F1 注册注入需求：实例级工厂、配置重载保留注册（formula1.cc:34）、重名报错、是否提供求值时上下文绑定。
  2. 多输出/状态：UDF 返回 double/缓存整列；分数+order+状态的绑定；LTR carry 用通用执行器还是前置参数序列。
  3. float32 逐位一致未验证：原语单测已见 float 转换、int 除法、-0 符号差异；近分时排序可翻转。
  4. AB 整组版本：入口选配置集 + 公式内 AB 条件；请求固定版本、旧版本生命周期。
  5. EMER 是否改异步；后续策略/GroupPK 是否接入同一引擎；epsilon 比较器非严格弱序。
